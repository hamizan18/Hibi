# Architecture decision records

## ADR-001: Offline-only Android foundation — 2026-11-26

Context: a single-user personal application must function without network access. Decision: Flutter Android-only, local Drift/SQLite, no backend or accounts. Alternatives: cloud synchronization or remote database. Consequences: no account recovery or cross-device synchronization; backups require explicit local data management. SQLite is not encrypted by default.

## ADR-002: Feature-first with injected dependencies — 2026-11-26

Context: incremental features need testable rules without needless complexity. Decision: presentation, application/state, domain and data responsibilities grouped by feature, with Riverpod for injection and an injectable clock. Alternatives: monolithic widgets or a full framework for every layer. Consequences: independently testable logic; create layers only where useful.

## ADR-003: Milestone-scoped dependencies — 2026-11-26

Context: preferred packages cover future functionality but are not all needed now. Decision: add only compatible packages needed by the active milestone; use Material 3, GoRouter, Riverpod and Drift for the foundation. Alternatives: install all planned packages immediately. Consequences: future dependency choices and versions remain subject to SDK compatibility and milestone approval.

## ADR-004: Development identity — 2026-11-26

Context: no final application ID was supplied. Decision: retain `com.example.hibi` as a development placeholder. Alternative: invent a production identifier. Consequence: confirm the permanent ID before public distribution; changing it affects Android application identity.

## ADR-005: Minimal explicit Drift schema — 2026-11-26

Context: the foundation needs persistence without creating future feature tables. Decision: Drift with a single explicit SQL settings table and no generated code. Native SQLite opens lazily in the application support directory; tests inject their own executor. Alternatives: generated Drift tables now or unused feature tables. Consequences: small initial dependency and schema surface, but queries do not have automatic table change notifications; introduce typed generated tables and explicit migrations as features require them.

## ADR-006: Local date presentation — 2026-11-26

Context: the foundation only displays one Japanese-style date format. Decision: use a small weekday mapping and an injected local clock; recalculate on resume and at the next local midnight. Alternative: introduce Intl as a direct dependency for this single format. Consequence: add Intl if later formatting requirements justify it; historical date storage remains a separate future responsibility.

## ADR-007: Dated habit identity schema — 2026-11-26

Context: habit identity and historical configuration must be separated without destroying existing settings. Decision: schema version 2 adds identity and name-version tables via an explicit transactional migration; ISO local dates use inclusive starts and exclusive ends, with SQLite overlap triggers and unique per-habit revision numbers. UTC creation instants use integer microseconds since the Unix epoch. Alternative: overwrite habit names or rely on application-only interval checks. Consequences: adjacent versions are valid and overlapping intervals are rejected even through direct SQL; application-level correction, auditing, typed target configuration and lifecycle rules remain necessary before exposing habit writes. Do not treat this partial schema as the completed habit engine.

## ADR-008: Exact counter target per habit version — 2026-11-26

Context: an initial measurable target needs deterministic precision and historical association without assuming targets for existing versions. Decision: a separate `habit_counter_targets` row belongs to one habit version; `CounterTarget` validates a positive integer and nonblank unit, and SQLite checks integer storage and positivity. Existing versions receive no inferred row during migration. Alternatives: floating-point quantities or unvalidated generic JSON. Consequences: counter quantities are whole signed 64-bit integers; decimal measurement targets need a separately documented representation. A low-level insert/read store exists but is not a user-facing editing workflow, audit mechanism or backdated correction authorization.

## ADR-009: Transactional counter version writes — 2026-11-26

Context: version writes must not silently rewrite history and must commit with local audit records. Decision: use a narrowly scoped `CounterHabitWriter` and schema version 4; create a habit/version/target/audit together, or close the latest open counter version and append a strictly future version with before/after audit snapshots in one transaction. Reject same-day and backdated edits until an explicit correction workflow exists. Alternative: expose the low-level target store directly or silently rewrite historical rows. Consequences: only counter creation and future append are supported, with injected local clock and caller-supplied IDs; raw SQL and the low-level store still bypass these safeguards. Audit is not tamper-proof and stores potentially sensitive names, units and quantities in unencrypted local storage. Privacy controls, permanent deletion, correction preview/confirmation, and recalculation must be designed before exposing this path to users.

## ADR-010: Historical correction requires an exact preview — 2026-11-26

Context: the present schema cannot preserve occurrence interpretation during a backdated change; historical records, audit, statistics and rewards must not be silently rewritten. Decision: design a typed preview/confirm flow tied to a snapshot of the full affected read set; revalidate inside one transaction, retain preimages and reconcile implemented derived data or reject the correction. Alternatives: overwrite versions or accept confirmation without checking concurrent changes. Consequences: no correction API or UI exists yet. Occurrence/event storage, immutable historical representation, privacy controls and reconciliation contracts must be designed and implemented before correction is enabled. Details and acceptance scenarios are in ARCHITECTURE.md and TEST_PLAN.md.

## ADR-011: Counter occurrence snapshots and events — 2026-11-26

Context: daily records must refer to the correct historical configuration and support multiple progress entries without creating fabricated failures. Decision: schema version 5 adds counter occurrences with unique habit/local-date keys, applicable-version and target-snapshot validation, plus multiple integer counter events with UTC timestamps. Triggers reject edits that would invalidate an existing occurrence. Alternatives: infer dates from event timestamps or derive old targets from mutable current configuration. Consequences: history is protected against those direct changes, but the schema alone does not implement schedules, lifecycle, occurrence generation, status, audited event corrections, privacy deletion or aggregates. Existing records are not populated during migration. Future correction/privacy workflows require explicit changes to these restrictions.

## ADR-012: Date-only recurrence evaluation — 2026-11-26

Context: schedule applicability must be deterministic across calendar boundaries without reinterpreting stored local dates on device time-zone changes. Decision: use validated Gregorian `LocalDate` components and pure daily/selected-ISO-weekday evaluators with an inclusive anchor and optional exclusive end. Alternatives: compare local midnight timestamps or consult the system clock during recurrence evaluation. Consequences: callers must select the relevant local date and combine the recurrence result with effective version and lifecycle state. At the time of this decision schedules were not persisted; low-level persistence was subsequently added in ADR-013. Monthly, interval and other recurrence rules need separate implementations.

## ADR-013: Version-scoped schedule persistence — 2026-11-26

Context: recurrence rules must remain associated with historical habit versions without inferring schedules for existing data. Decision: schema version 6 stores one daily or selected-weekday schedule per version, with validated ISO dates and a bounded seven-bit ISO weekday mask; absent rows remain unconfigured. A low-level store maps the typed evaluator to this representation. SQLite triggers refuse schedule writes on versions already referenced by occurrences. Alternatives: default existing versions to daily or store unvalidated generic JSON. Consequences: existing history is not silently assigned a schedule, but version creation, audit, lifecycle and recurrence checks are not yet integrated with this store; corrections and privacy deletion require explicit future workflows.

## ADR-014: Effective-dated lifecycle and three-way applicability — 2026-11-26

Context: pause, archive and delete must not become false failures, and migrated versions have no trustworthy lifecycle or schedule by default. Decision: schema version 7 adds append-oriented effective-dated lifecycle events with previous/new state, reason and UTC timestamp. An internal reader combines lifecycle, effective version and stored recurrence and returns `applicable`, `notApplicable` or `unknown`. Backdated and same-day duplicate transitions are rejected, and existing later occurrences block lifecycle inserts. Alternatives: a single mutable `isActive` flag or interpreting missing data as active. Consequences: missing configuration stays unknown; conservative restrictions require a future explicit correction/privacy deletion workflow. Direct SQL can bypass transition validation; lifecycle is not yet wired to notifications, habit creation, occurrence generation or UI.

## ADR-015: Complete initial counter creation — 2026-11-26

Context: a habit version without an explicit schedule and lifecycle event cannot be evaluated reliably. Decision: `CounterHabitWriter.create` requires a caller-supplied schedule and lifecycle event ID, and writes the habit, version, target, schedule, initial active event and audit snapshot in one transaction using one captured clock instant. The active event is effective on the selected habit start date; a future start is not applicable beforehand and no separate scheduled event is guessed. An already-ended schedule is rejected. Alternatives: infer a daily schedule or write configuration in separate transactions. Consequences: callers must explicitly supply a schedule; no defaults or occurrence records are created. The separate future-version path does not yet attach a schedule and is not a complete user-facing editing workflow.

## ADR-016: Explicit schedule on future counter versions — 2026-11-26

Context: a future version without its own schedule cannot be evaluated, and silently copying an older schedule could misrepresent the user's choice. Decision: require the caller to provide a schedule and write it in the existing future-version transaction, together with target, version boundaries and before/after audit snapshots. A missing previous schedule stays missing and is captured as null. Reject schedules ending on or before the new version starts. Alternatives: silently default to daily or copy the previous recurrence. Consequences: historical schedules and occurrences remain associated with their versions; callers must supply the full intended recurrence and anchor. Occurrence generation, UI and historical correction are still unimplemented. This supersedes the earlier statements that future-version creation does not attach a schedule.

## ADR-017: On-demand counter occurrences — 2026-11-26

Context: consumers need deterministic per-date records without a background generator, fabricated failures or duplicate occurrences. Decision: an internal transactional store combines the existing applicability reader with version/target lookup, returns an existing snapshot unchanged, and inserts a caller-identified occurrence only for a known applicable counter date. Missing target configuration yields `unknown`; existing records remain visible even when applicability is unknown or not applicable. Alternatives: populate dates ahead of time or treat missing configuration as failure. Consequences: no status or progress is inferred, and callers must handle applicability and occurrence independently. This is not an audited progress or historical-correction workflow, and is not exposed in UI.

## ADR-018: Same-day audited counter progress — 2026-11-26

Context: several progress entries must survive independently, while historical corrections require a separate confirmation workflow. Decision: schema version 8 adds an event-creation audit snapshot keyed by the event ID; an internal writer atomically appends the event and snapshot with one injected UTC timestamp, accepting positive integer quantities for an applicable occurrence on the current local date. Reject duplicate IDs and sums exceeding signed 64-bit range. Existing events gain no invented audits during migration. Alternatives: overwrite a daily total or silently allow historical writes. Consequences: users cannot yet log missed prior dates through this path; historical correction, status and UI remain unimplemented. Direct SQL can bypass the writer and audit protections; snapshots are not encrypted or tamper-proof.

## ADR-019: Derive counter progress from recorded events — 2026-11-26

Context: counter events may be recorded separately and must be interpreted against the target that applied to their occurrence, without inventing failures. Decision: pure domain logic derives pending for no events, partial below target and completed at or above target; a read-only adapter retrieves the occurrence's snapshot and events together. Invalid positive-integer inputs or a signed 64-bit overflow are rejected. A missing occurrence returns no result. Alternatives: store a mutable daily status or use the latest habit target. Consequences: results are reproducible from source records and preserve excess progress, but do not represent applicability, explicit failure, recovery or excusal; callers must resolve these separately. No UI or persisted derived status is introduced.

## ADR-020: Compose applicability and recorded counter progress — 2026-11-26

Context: existing historical records must remain visible without treating unknown schedules, paused dates or missing occurrences as failures. Decision: read schedule/lifecycle applicability and any existing occurrence/progress in one transaction, returning them as separate fields without creating data. A missing occurrence has no recorded progress even if the schedule applies. Alternatives: synthesize pending records or discard progress when a date is not applicable. Consequences: callers must explicitly interpret applicability and recorded data together; applicability alone does not establish that a missing counter target is configured. Explicit failure, recovery, excusal and UI remain unimplemented.

## ADR-021: Explicit counter resolution — 2026-11-26

Context: failed and excused must be explicit without overwriting progress or silently changing historical results. Decision: schema version 9 adds one immutable resolution creation record per occurrence; it doubles as a local audit snapshot of state, optional reason, target, progress and UTC instant. The internal writer permits only applicable current-local-date occurrences with incomplete progress. Duplicate resolution and subsequent progress via the internal writer are rejected until a correction workflow exists. The day reader returns resolution independently from applicability and recorded progress. Alternatives: infer failure from missing records or overwrite progress. Consequences: no historical correction, recovery or UI is implemented; direct SQL can bypass application checks, and immutable triggers need a deliberate privacy-deletion/correction design. Existing records receive no inferred resolutions.

## ADR-022: Effective counter-day status and conflict preservation — 2026-11-26

Context: callers need a deterministic day status that combines applicability, missing occurrences, recorded progress and explicit resolutions without fabricating pending occurrences or hiding contradictory historical records. Decision: add pure `interpretCounterDay` and read-only `CounterDayReader.evaluate`, checking the applicable version's configured `CounterTarget` when no occurrence exists; return `notApplicable`, `unknown`, `pending`, `partial`, `completed`, `failed`, `excused` (and later `recovered`), or `conflict` when records coexist with `notApplicable`/`unknown` applicability or mismatched resolution snapshots, while always retaining the full underlying `CounterDay` and optional `configuredTarget`. Alternatives: synthesize occurrence rows on read or let `notApplicable`/`unknown` silently hide existing occurrences. Consequences: missing occurrences on configured applicable dates report `pending` with `hasOccurrence == false`; legacy applicable versions without a counter target report `unknown`; contradictory raw-SQL or legacy states surface explicitly as `conflict`.

## ADR-023: Bounded counter recovery domain calculation — 2026-11-26

Context: counter recovery must support partial and multiple entries against an eligible failed deficit without exceeding that deficit or overwriting original same-day progress. Decision: add pure `CounterRecovery` and `CounterRecoveryStatus` (`unrecovered`, `partiallyRecovered`, `recovered`), accepting only explicitly `failed` occurrences with incomplete progress (`initialDeficit = target - recordedTotal > 0`) and positive integer recovery quantities whose cumulative sum does not exceed `initialDeficit`. Alternatives: fold recovery quantities into same-day `CounterProgress` or allow recovery on unresolved/excused occurrences. Consequences: original `recordedTotal`, `recoveredTotal` and `remainingDeficit` remain separate deterministic facts; excess or non-positive quantities and ineligible statuses are rejected.

## ADR-024: Immutable audited counter recovery records — 2026-11-26

Context: partial and multi-step recoveries need persistent audit snapshots tied to the original failed occurrence without mutating same-day events or today's independent occurrence. Decision: schema version 10 adds `habit_counter_recoveries` with immutable update/delete triggers; each row stores the original occurrence ID, current `recovery_local_date`, positive `quantity`, `original_target_count`, `original_progress_total`, resulting `remaining_deficit`, optional `note` and UTC timestamp. `CounterRecoveryWriter` permits recovery only on a later local date when the original occurrence date was applicable, the habit is currently `active`, the occurrence is explicitly resolved as `failed` with matching snapshots, and cumulative quantities stay within the deficit. Alternatives: mutate the resolution row in place or insert synthetic counter events on the original date. Consequences: full step-by-step recovery audit is preserved in unencrypted SQLite; migrations from versions 1–9 invent no recoveries; direct SQL can still insert inconsistent rows, and future correction/privacy-deletion workflows must explicitly handle the immutable triggers.

## ADR-025: Integrate counter recovery into day status evaluation — 2026-11-26

Context: reading a prior counter day should reflect whether an explicit failure remains unrecovered, is partially recovered, or has been fully recovered, while detecting tampered recovery rows. Decision: include ordered `CounterRecoveryRecord` entries on `CounterDay` and optional `CounterRecovery` on `CounterDayEvaluation`; transition effective status from `failed` to `recovered` only when valid recovery entries reduce `remainingDeficit` to zero, keep partially recovered days as `failed` with recovery progress attached, and report `conflict` if recovery rows exist on unresolved/excused/completed occurrences, on or before the occurrence date, or with inconsistent snapshots/deficits. Alternatives: overwrite `resolution.state` or ignore invalid raw-SQL recovery records. Consequences: consumers see both the historical failure and the exact recovery state without losing same-day totals or today's independent target.

## ADR-026: Read-only multi-habit counter day roster — 2026-11-26

Context: dashboard and history readers need a consistent per-date view across all stored habits without N separate transactions or side-effecting occurrence creation. Decision: add `CounterDayRosterReader.readForDate`, which reads all habits in deterministic `(created_at_utc_us, id)` order inside one read transaction, pairing any applicable version metadata (`versionId`, `name`, `revision`) on that date with `CounterDayReader.evaluate`. Alternatives: auto-create occurrences while listing a date or omit habits that are not applicable/unknown. Consequences: callers receive a complete, deterministic, side-effect-free snapshot of all habits for a date; UI and multi-date history readers remain separate tasks.

## ADR-027: Read-only counter date-range history and recoverable-deficit queries — 2026-11-26

Context: history views and recovery workflows need to inspect a habit across an inclusive calendar range and locate prior failed occurrences that still have remaining recovery deficits without creating occurrences or inferring failures. Decision: add `CounterHistoryReader.readRange` (stepping pure Gregorian calendar dates in one read transaction) and `CounterHistoryReader.findRecoverableDeficits` (returning prior occurrences whose evaluated status is `failed` with positive `remainingDeficit` only when the habit's latest lifecycle state on `asOfDate` is `active`). Alternatives: query raw occurrence rows without status/conflict evaluation or return deficits while a habit is paused/archived. Consequences: range history and eligible recovery targets are deterministic and side-effect-free; cross-habit analytics remain in Milestone 2.

## ADR-028: Transactional current-day counter action coordinator — 2026-11-26

Context: calling `CounterOccurrenceStore.getOrCreate` separately from `CounterProgressWriter.append` or `CounterResolutionWriter.resolve` would leave an empty occurrence row committed if the subsequent event or resolution failed. Decision: add `CounterTodayActionService`, which wraps on-demand occurrence retrieval/creation and same-day progress or explicit resolution inside one database transaction using one captured clock instant, and returns the updated `CounterDayEvaluation` (alongside a transactional `recoverPriorDeficit` method). Alternatives: require callers to manage multi-store transactions manually. Consequences: failed progress or resolution attempts roll back any newly created occurrence atomically; same-day actions remain bounded to the current local date from the injected clock.

## ADR-029: Detailed lifecycle history and applicability reasons — 2026-11-26

Context: callers need to distinguish why a date is `notApplicable` (`beforeStart`, `scheduled`, `paused`, `archived`, `deleted`, `unscheduled`) or `unknown` (`missingVersions`, `missingLifecycle`, `missingActiveVersion`, `missingSchedule`), and inspect dated lifecycle transitions without mutating state. Decision: add `HabitLifecycleEvent`, `HabitLifecycleReader` (`findEffectiveOn`, `readHistory`) and `HabitApplicabilityReader.describe`, keeping `HabitApplicabilityReader.evaluate` backward-compatible. Alternatives: infer reasons outside the transaction or add redundant schema columns. Consequences: lifecycle history and applicability reasons are available in one read transaction without schema changes.

## ADR-030: Optional editable counter starter templates — 2026-11-26

Context: `PROJECT_SPEC.md` and `BUSINESS_RULES.md` specify optional, editable counter starter templates (`Quran Reading` / `N`, 5 pages daily; `Push Up` / `P`, 10 repetitions daily) that must never auto-populate user records or seed history. Decision: add pure `CounterStarterTemplate` definitions with `copyWith` validation and `CounterHabitWriter.createFromStarterTemplate`, which delegates to transactional habit creation only when explicitly called for today or a future date. Alternatives: seed starter habits during database creation or hardcode uneditable template writers. Consequences: skipping templates writes zero rows, editing templates before creation is validated and audited, and avoidance/checklist starter templates remain deferred to their respective tracking-type implementations.

## ADR-031: Riverpod providers for internal counter habit services — 2026-11-26

Context: the architecture uses Riverpod to inject `AppDatabase` and `AppClock` into domain/data services and controllers for deterministic testing and future UI wiring. Decision: add `lib/features/habits/application/counter_habit_providers.dart` exposing providers for lifecycle, applicability, counter writer, occurrence, progress, resolution, recovery, day/roster/history readers, `CounterTodayActionService`, and read-only `counterDayRosterProvider` / `counterTodayRosterProvider`. Alternatives: instantiate readers and writers directly inside widgets or expose unfinished UI screens prematurely. Consequences: all counter services are injectable and testable via `ProviderContainer` overrides while the main navigation continues to mark unfinished UI sections accurately.

## ADR-032: Read-only counter configuration and version-timeline reader — 2026-11-26

Context: callers need a consistent snapshot of a counter habit's effective version, counter target, schedule, lifecycle history, prior versions and scheduled future versions as of a given local date without mutating data or guessing missing legacy configuration. Decision: add `CounterVersionSnapshot`, `CounterHabitConfiguration` and `CounterConfigurationReader` (`read`, `readAll`), partitioning versions relative to `asOfDate` and leaving missing target/schedule rows `null` in one read transaction. Alternatives: query versions, targets, schedules and lifecycle in separate transactions or synthesize default targets. Consequences: version timelines and legacy gaps are inspected deterministically without writes.

## ADR-033: Read-only counter audit trail reader — 2026-11-26

Context: Milestone 1 requires creation, version changes, lifecycle transitions, progress events, resolutions and recoveries to be auditable after restart without fabricating audit history for pre-migration records. Decision: add `CounterAuditReader.readForHabit`, reading `habit_version_audit`, `habit_lifecycle_events`, `habit_counter_event_audit`, `habit_counter_resolutions` and `habit_counter_recoveries` in one read transaction in chronological order. Alternatives: infer synthetic event audits from `habit_counter_events` rows lacking an audit entry. Consequences: only genuine persisted audit snapshots are returned, and all five streams survive disk database close and reopen.

## ADR-034: Semantic counter lifecycle action service — 2026-11-26

Context: raw lifecycle appends allow `active` from `scheduled`, `paused`, `archived` or `deleted`, which does not distinguish user intent between `resume` (from `paused`) and `restore` (from `archived` or `deleted`). Decision: add `CounterLifecycleActionService` with explicit `pause`, `resume`, `archive`, `softDelete` and `restore` methods that validate the current lifecycle state inside one transaction, append the dated lifecycle event, and return the updated `CounterHabitConfiguration`. Alternatives: let callers pass raw `HabitLifecycleState.active` without checking whether the habit was paused versus archived/deleted. Consequences: mismatched semantic actions are rejected atomically while all historical occurrences and progress remain intact.

## ADR-035: Pure counter date-range summary and separated quantity totals — 2026-11-26

Context: summarizing a counter habit across a date interval must keep `pending` (both missing-occurrence and zero-progress), `unknown`, `notApplicable` and `conflict` distinct from `failed`, and must not mix recovered quantities into same-day recorded progress. Decision: add pure `CounterRangeSummary.fromEvaluations`, counting each `CounterDayEffectiveStatus`, splitting pending days into missing-occurrence versus recorded-zero, excluding `conflict` rows from valid quantity totals, and tracking `recordedQuantityTotal`, `recoveredQuantityTotal` and `remainingDeficitTotal` separately with 64-bit overflow checks. Alternatives: fold recovered quantities into recorded totals or treat pending/no-data ranges as 0% failed. Consequences: range summaries expose explicit data-availability flags without fabricating scores or double-counting recovery.

## ADR-036: Read-only counter habit overview reader — 2026-11-26

Context: inspecting a single counter habit requires its configuration/version timeline, current-day status evaluation, date-range history, range summary and recoverable prior deficits from one consistent database snapshot. Decision: add `CounterHabitOverviewReader.read` and wire `counterConfigurationReaderProvider`, `counterAuditReaderProvider`, `counterLifecycleActionServiceProvider` and `counterHabitOverviewReaderProvider` in `counter_habit_providers.dart`. Alternatives: issue multiple independent transactions that could observe different database states. Consequences: complete single-habit inspection runs in one read-only transaction with zero writes.

## ADR-037: Read-only multi-habit counter dashboard summary reader — 2026-11-27

Context: a daily dashboard needs each stored counter habit's roster evaluation, specific applicability reason, prior recoverable deficits (only when the habit is active on that date), and aggregate day summary from a single read snapshot. Decision: add `CounterDashboardReader.readForDate`, combining `CounterDayRosterReader`, `HabitApplicabilityReader.describe`, `CounterHistoryReader.findRecoverableDeficits` and `CounterRangeSummary.fromEvaluations` in one read transaction. Alternatives: run separate per-habit transactions or auto-create occurrences when loading the dashboard. Consequences: dashboard reads are atomic and side-effect-free.

## ADR-038: Read-set-bound counter historical correction preview — 2026-11-27

Context: backdated target corrections must preview exact affected ranges and occurrence impacts and must fail safely if any underlying data or the local calendar day changes before confirmation. Decision: add `CounterCorrectionPreviewer`, which validates unit compatibility and resolution/recovery consistency, computes per-occurrence status transitions, marks unimplemented derived engines (`score`, `streak`, `reward`, `achievement`) explicitly as `notImplemented`, generates an English confirmation summary, and binds a deterministic JSON `snapshotSignature` covering the local date, version, target, schedule, lifecycle, occurrences, events, resolutions and recoveries. Alternatives: bind confirmation only to a version ID or allow unit changes to reinterpret history. Consequences: any concurrent source mutation or midnight boundary makes the preview stale.

## ADR-039: Atomic counter historical correction commit and preimage audit — 2026-11-27

Context: confirming a counter target correction must update the version target and affected occurrence target snapshots while preserving full before/after preimages and keeping direct-SQL protection triggers active. Decision: schema version 11 adds immutable `habit_counter_correction_audit`; `CounterCorrectionWriter.commit` revalidates that the confirmed preview is not stale inside one SQLite write transaction, updates `habit_counter_targets` and `habit_occurrences` while recreating the protection triggers in that same transaction, and records full JSON before/after preimages without modifying source `habit_counter_events`. Alternatives: delete protection triggers permanently or overwrite source events. Consequences: failed or stale commits roll back completely, source events remain intact, and direct SQL updates remain blocked.

## ADR-040: Extended date-only recurrence evaluation and 5-column schedule persistence — 2026-11-27

Context: Milestone 1 requires custom day intervals, monthly day-of-month schedules (default skip or optional last-day fallback) and one-time schedules without breaking existing 5-column `habit_schedules` queries. Decision: extend `HabitSchedule` with `IntervalSchedule`, `MonthlyDaySchedule` and `OneTimeSchedule`, and upgrade `habit_schedules` in schema version 11 to accept `'interval'`, `'monthly_skip'`, `'monthly_last_day'` and `'one_time'` while preserving the 5-column layout and existing rows. Alternatives: use timestamp arithmetic or break positional 5-column SQL compatibility. Consequences: leap years, nonexistent monthly dates and custom intervals evaluate deterministically on pure Gregorian calendar dates.

## ADR-041: Version-scoped habit metadata and priority weights — 2026-11-27

Context: habits require versioned description, symbol, category, priority (`Critical 4`, `High 3`, `Normal 2`, `Low 1`), privacy, recovery/score/streak/reward inclusion flags and display order without guessing values for migrated versions. Decision: add `HabitPriority`, `HabitMetadata`, `HabitMetadataStore` and `habit_version_metadata` in schema version 11, with triggers blocking unconfirmed edits once occurrences exist. Alternatives: store untyped JSON blobs or assign default categories during migration. Consequences: legacy versions without metadata remain `null` until explicitly configured.

## ADR-042: Independent multi-checklist habit engine and Daily Prayers template — 2026-11-27

Context: multi-checklist habits require independent item statuses, partial completion when some items are done, and per-item prior-date recovery without overwriting same-day logs or auto-seeding records. Decision: add `ChecklistItemDefinition`, `ChecklistDayProgress`, `ChecklistStarterTemplate.dailyPrayers` (`S`: Fajr, Dhuhr, Asr, Maghrib, Isha) and `ChecklistHabitService` backed by `habit_checklist_items`, `habit_checklist_occurrences`, `habit_checklist_item_logs` and `habit_checklist_item_recoveries` in schema version 11. Alternatives: collapse checklist progress into a single boolean or counter. Consequences: each checklist item retains its own log and recovery audit trail.

## ADR-043: Avoidance habit engine, daily confirmation and Self Control template — 2026-11-27

Context: avoidance habits support repeated incidents and a configurable maximum (`maxIncidents >= 0`), must never enable recovery, and must not treat zero incidents as confirmed success without daily confirmation. Decision: add `AvoidanceTarget`, `AvoidanceDayProgress`, `AvoidanceStarterTemplate.selfControl` (`O`: max 0, private, no recovery) and `AvoidanceHabitService` backed by `habit_avoidance_targets`, `habit_avoidance_occurrences`, `habit_avoidance_incidents` and `habit_avoidance_resolutions`. Alternatives: auto-complete avoidance days with zero incidents or allow recovery. Consequences: exceeding `maxIncidents` fails immediately while still recording subsequent incidents; unconfirmed days within the limit remain `pending`.

## ADR-044: Boolean and duration (manual and timer) tracking engines — 2026-11-27

Context: Milestone 1 requires simple boolean habits and duration habits supporting both manual seconds and validated start/end timer intervals. Decision: add `BooleanLogState`, `DurationTarget`, `DurationEntryInput` (`manual` and `timer`), `DurationDayProgress` and `BooleanDurationHabitService` backed by `habit_typed_targets`, `habit_typed_occurrences`, `habit_duration_events` and `habit_typed_logs`. Alternatives: store floating-point minutes or discard timer start/end timestamps. Consequences: duration progress is exact whole seconds and timer entries enforce `endedAtUtc > startedAtUtc`.

## ADR-045: Fixed-scale measurement, time-of-day and range tracking engines — 2026-11-27

Context: measurement, time-of-day and range habits require typed validation and exact precision without floating-point rounding bugs. Decision: add `MeasurementTarget` (signed 64-bit integer `scaledTarget` with `decimalPlaces` 0..6 and `atLeast`/`atMost`/`exact` rule), `TimeOfDayTarget` (`0..1439` minutes since local midnight with `atOrBefore`/`atOrAfter` rule), `RangeTarget` (`[minScaled, maxScaled]` with `decimalPlaces` 0..6) and `MeasurementTimeRangeHabitService`. Alternatives: store IEEE-754 floats or unvalidated strings. Consequences: all typed targets and logs are validated by both Dart domain objects and SQLite `CHECK` constraints.

## ADR-046: Unified starter template catalog and multi-type habit registry — 2026-11-27

Context: callers and providers need a single catalog of all four approved starter templates (`O`, `N`, `S`, `P`) and a read-only registry that identifies any habit version's tracking type, metadata, schedule and applicability on a date. Decision: add `StarterTemplateCatalog`, `UnifiedHabitRegistryReader` and corresponding Riverpod providers in `counter_habit_providers.dart`. Alternatives: scatter template constants or guess tracking types when target rows are absent. Consequences: all eight tracking types (`counter`, `checklist`, `avoidance`, `boolean`, `duration`, `measurement`, `timeOfDay`, `range`) plus `unconfigured` legacy versions are inspected uniformly in one read transaction.

## ADR-047: Transactional non-counter creation snapshots — 2026-11-27

Context: checklist, avoidance and typed creation paths wrote lifecycle events but omitted a complete creation audit. Decision: write a `habit_version_audit` creation snapshot from the persisted version, schedule, optional metadata, initial lifecycle, typed target or ordered checklist items inside the same creation transaction. Reuse the version creation timestamp and generate an audit ID without changing public service signatures. Alternatives: backfill current values for existing records or audit only in the UI. Consequences: failed audit insertion rolls back creation; existing unaudited records remain untouched and cannot be represented as having a historical snapshot. Audit data is local and unencrypted; no migration or privacy access control is introduced.

## ADR-048: Historical recovery eligibility and visibility — 2026-11-27

Context: recovery must use the failed occurrence's historical settings and must not reveal a prior private configuration when its current version is public. Decision: Today recovery eligibility checks the original version's explicit recovery flag, item flag where applicable, original applicability and current active lifecycle, and revalidates before writing in the same transaction. Missing metadata is ineligible. Historical private labels and quantities are hidden unless the user explicitly reveals private habits. Alternatives: assume recovery is enabled for legacy data or use current metadata for old records. Consequences: no backfill, no synthetic failures, no change to today's independent progress; the visibility switch is not authentication and lower-level writers still require disciplined callers.

## ADR-049: Audited pause from initial start — 2026-11-27

Context: initial active lifecycle events may be future-dated and immutable, preventing a user from pausing from the first scheduled day. Decision: schema version 12 adds an immutable start-pause record linked to the original event. After confirmation, the service verifies the original event, first-version start, local date and absence of occurrences in one transaction. Effective lifecycle readers order the original active event and the pause on the same date; later ordinary transitions use the resulting state. Counter correction previews include the new record in their stale-read signature. Alternatives: rewrite the original event or silently start active and pause a day later. Consequences: history and source records remain addressable; this is pause, not permanent cancellation, and direct SQL can bypass service validation. Privacy deletion and Android migration validation remain outstanding.
