# Architecture

The intended design is feature-first with only the layers each feature needs. Presentation owns screens, interaction and UI state, and must not issue SQL. Riverpod providers/controllers coordinate operations and inject dependencies. Domain owns entities, calculations and rules, preferably pure Dart. Data owns repositories, Drift DAOs and mappings. Core contains shared database, clock, errors, security, services and widgets. Dependencies flow inward toward domain; avoid cycles, duplicated rules, God classes and needless abstractions.

The foundation uses Flutter, Material 3, Riverpod, GoRouter and Drift/SQLite as required by Milestone 0. Inject repositories, the clock and services for deterministic tests. Navigation groups planned features into Today, History, Finance, Growth and More. Features not yet built must not appear operational.

Path Provider supplies the local database directory. Future candidate packages include Intl, FL Chart, Table Calendar, Flutter Local Notifications, Local Auth, Flutter Secure Storage, File Picker, Share Plus, PDF and Printing. Add only when the active milestone requires them and compatibility has been checked; these are not claims that packages or features are installed. Flutter Test and Integration Test support appropriate tests. See DECISIONS.md and DATABASE_SCHEMA.md for decisions and persistence constraints.

The counter progress, bounded recovery, date-range summary (`CounterRangeSummary`), multi-checklist (`ChecklistDayProgress`), avoidance (`AvoidanceDayProgress`), boolean/duration (`DurationDayProgress`), fixed-scale measurement/time-of-day/range targets and optional editable starter-template definitions (`StarterTemplateCatalog`) are pure domain logic. `HabitMetadataStore` persists version-scoped category, symbol, priority, privacy, inclusion flags and display order, while `HabitScheduleStore` persists daily, weekday, custom day-interval, monthly (skip or last-day fallback) and one-time recurrences. `CounterDashboardReader` and `UnifiedHabitRegistryReader` inspect multi-habit daily state and tracking types in single read-only transactions. `CounterCorrectionPreviewer` and `CounterCorrectionWriter` implement read-set-bound historical counter target correction previews, stale-snapshot detection across data and local-day boundaries, and atomic preimage/postimage audit commits. Riverpod providers in `lib/features/habits/application/counter_habit_providers.dart` wire all Milestone 1 stores, readers and services to `databaseProvider` and `appClockProvider`.

`HabitBuilderScreen` is reachable from Today and More. It validates form input, selects optional editable templates and calls the existing injected services; counter creation and version metadata insertion share a transaction. Measurement and range inputs are converted directly from decimal text to scaled integers. The screen creates no occurrences and warns that privacy controls and database encryption are unavailable.

Non-counter creation services write their version, target or checklist items, schedule, optional metadata, lifecycle and creation audit in one transaction. The audit serializes the persisted configuration and does not infer snapshots for older records.

Today uses a read-only `UnifiedHabitRegistryReader` roster and separate current-day cards for each tracking type. Read-only adapters load typed configuration and results without creating occurrences; explicit actions call the existing services. Missing configuration and conflicting records do not become failures. Private and unclassified habits are hidden until the user explicitly reveals them; this is not authentication. Duration timers exist only in the current screen state and may be discarded on navigation, resume or visibility changes.

Today exposes dated lifecycle controls for all configured tracking types and separate counter/checklist prior-date recovery controls. Lifecycle actions reuse the existing semantic transition service and append-only store; the store rejects transitions that would reinterpret recorded non-counter occurrences. The database trigger independently protects counter occurrences only, so direct SQL is not a safe lifecycle authorization path. The recovery eligibility services check the original version's explicit recovery metadata and revalidate candidates in the same transaction as the write; unknown metadata is not treated as consent. Historical private recovery details remain hidden until explicitly revealed. These UI eligibility checks do not make raw SQL or lower-level writers safe authorization paths.

Before the first version's start, `UnifiedHabitRegistryReader` returns that first version's name, type, metadata and schedule for management, while retaining `beforeStart` applicability for the requested date. It does not select a future version for a gap after an earlier version. Today applies the same private/unclassified visibility filter and never offers logging before start. A confirmed pause from start adds an immutable record linked to the original initial active event; effective lifecycle reads include both events in order on the start date, without rewriting the original. The service transaction verifies the exact initial event, the local date, the first version and the absence of occurrences before writing. Ordinary later transitions retain their existing restrictions.

For counter habits on Today, `CounterFutureVersionControls` displays the effective version and scheduled future versions from `CounterConfigurationReader` and schedules strictly future counter versions (including optional `HabitMetadata` and before/after audit snapshots) via `CounterHabitWriter.scheduleVersion` without altering prior versions or occurrences. `CounterCorrectionControls` previews counter target corrections via `CounterCorrectionPreviewer` and `AnalyticsCorrectionImpactReader`, presenting an English confirmation dialog detailing the affected half-open date range, per-occurrence status changes, recalculated daily weighted score and streak impacts, and unimplemented reward/achievement engines, and commits confirmed previews atomically via `CounterCorrectionWriter` (rejecting stale previews). `CounterAuditHistoryControls` opens a read-only inspector (`CounterAuditHistorySheet`) combining `CounterHabitOverviewReader` (7-day range summary and daily evaluations) and `CounterAuditReader` (all six persisted audit streams, including `correctionAudits`), redacting private history when private visibility is off. For all seven non-counter tracking types (`checklist`, `avoidance`, `boolean`, `duration`, `measurement`, `timeOfDay`, `range`), `NonCounterVersionAndAuditControls` and `NonCounterAuditHistorySheet` (backed by `NonCounterVersionService`) provide strictly future version scheduling with before/after `habit_version_audit` snapshots and read-only version/lifecycle/audit inspection with private redaction.

For Milestone 2 — History and analytics, pure domain calculators in `lib/features/habits/domain/habit_analytics.dart` (`UnifiedHabitDayEvaluation`, `HabitAnalyticsFilter`, `DailyWeightedScoreCalculator`, `HabitStreakEvaluator`, `AnalyticsPeriodReportCalculator`) compute priority-weighted daily scores (`Critical 4`, `High 3`, `Normal 2`, `Low 1`), habit-level recording coverage, item-level checklist coverage, calendar heatmap cells, period reports and scheduled-occurrence streaks (`completedOnly` and `completedAndRecovered`) without persisting mutable derived rows. Read-only data services in `lib/features/habits/data/unified_habit_history_reader.dart` (`UnifiedHabitHistoryReader`) and `lib/features/habits/data/habit_analytics_reader.dart` (`HabitStreakReader`, `CalendarHeatmapReader`, `AnalyticsReportReader`, `AnalyticsCorrectionImpactReader`) evaluate all eight tracking types over any requested date or interval in single read transactions with zero occurrence writes. `HistoryAnalyticsView` (`lib/features/habits/presentation/history_analytics_screen.dart`), wired to the `/history` navigation tab in `lib/app/app.dart`, renders period/category/type/habit filters, private-visibility redaction by default, an interactive calendar heatmap, selected-day inspection, period summary reports and scheduled-occurrence streak cards.

Dashboard streaks treat every private or unclassified historical date as a privacy boundary when private visibility is off: the visible streak is calculated only from the public segment after the last such date. Explicit reveal includes the full history. Changing private visibility replaces the History snapshot rather than displaying a previous snapshot during the replacement read; an older asynchronous response cannot restore it.

Counter correction audits created by the current writer link to their predecessor and capture source-resolution and recovery preimages. The day reader uses the linked audit chain to interpret immutable resolution/recovery snapshots against the corrected target, and subsequent recovery remains bounded by the current deficit. Multiple unlinked legacy audits cannot be ordered reliably and remain `conflict`; they are not automatically rewritten. Correction impact previews exclude private/unclassified contributions unless explicitly revealed. Analytics-bound previews retain a private snapshot of habit tables and validate it inside the correction transaction; any habit-table change conservatively invalidates the preview, including changes unrelated to the displayed impact.

## Dynamic normalized scoring

The owner approved Dynamic Normalized Scoring and explicitly selected N/A for historical scores without valid configuration. The implementation has host-side automated coverage and a debug APK build; Android device verification and explicit Milestone 2 acceptance remain outstanding.

- **Measurement:** for a positive minimum target `T`, use `clamp(actual / T, 0, 1)`. Proposed maximum rule for nonnegative quantities: a value at or below the maximum earns `1`; above a positive maximum use `clamp(T / actual, 0, 1)`. For maximum `T = 0`, positive actual earns `0`. For minimum `T = 0`, an actual value meeting the target earns `1`; otherwise the normalized score is unavailable. For negative targets, a value meeting the target earns `1`, but a miss has no approved ratio or baseline: retain the recorded status and expose the score as unavailable, not zero. The existing exact comparison has no approved normalized formula.
- **Time-of-day:** a positive per-version tolerance is stored in whole minutes. Score is `clamp(1 - deviation / tolerance, 0, 1)` for before/after/near. An explicit relative day offset disambiguates directional comparisons across midnight; near uses the shorter circular clock distance and completes only at the exact target minute. Existing logs have local occurrence dates and wall-clock minutes but lack a logged relative-day offset and historical timezone context; these are not inferred from today's timezone.
- **Range:** within the inclusive target range score `1`; outside, `deviation` is the distance to the nearest endpoint and score is `clamp(1 - deviation / tolerance, 0, 1)`. Store tolerance as a positive fixed-scale integer in the same unit and scale as the range. Compute differences and ratios without signed 64-bit overflow.
- **Status and score:** keep recorded completion status separate from nullable normalized score. Pending, excused, unknown and conflicting records do not gain a synthetic score. An unavailable scoring rule is distinct from zero and is excluded from the weighted denominator with a visible incomplete-scoring indicator (and prevents a 100% day from classifying as `HeatmapIntensity.full`, labeling the heatmap cell `(partial score)`). This requires changing the current status-based `scoreMultiplier` contract, especially for time-of-day misses that may now earn nonzero credit.
- **Versioning and migration:** schema v13 adds scoring configuration keyed to `habit_version_id`, with rule version and validated type-specific tolerance; typed time logs carry a nullable relative day offset. The migration copies typed targets to support the `near` rule and preserves old logs without guessing offsets or scoring configurations. Future changes create a new effective-dated habit version; backdated changes require preview, audit and reconciliation. The `near` rule also affects creation/versioning, logging, Today and audit readers.
- **Historical policy:** derived scores were not stored as immutable snapshots. Historical measurement/time/range versions without valid scoring configuration retain their raw values and completion statuses but have score N/A; no tolerance or scoring config is backfilled. N/A is excluded from score aggregates and exposed separately in score coverage. The displayed aggregate for past dates can therefore change. New time/range versions require an explicitly entered positive tolerance.
- **Dependencies:** History, weighted score, coverage/heatmap/report and correction preview must consume the same versioned evaluator. Streak status and future XP/achievement rules remain separate; future Gamification must reference its own rule version and must not infer XP from numeric scores.

## Finance (Milestone 3)

Finance follows the same feature-first architecture under `lib/features/finance/`:
- **Domain (`lib/features/finance/domain/finance_models.dart`)**: pure integer-rupiah (IDR) arithmetic with signed 64-bit overflow/underflow checks (`checkedAddIdr`, `checkedSubIdr`), non-floating-point IDR formatting (`formatIdr`), immutable value objects (`FinanceWallet`, `FinanceCategory`, `FinanceTransaction`, `FinanceTransfer`, `FinanceBudget`, `FinanceAuditRecord`), and pure calculators (`FinanceBalanceCalculator`, `FinanceBudgetCalculator`, `FinanceReportCalculator`).
- **Data (`lib/features/finance/data/finance_service.dart`)**: transactional SQLite service backed by schema v14 tables (`finance_wallets`, `finance_categories`, `finance_transactions`, `finance_transfers`, `finance_budgets`, `finance_audit`). Every write validates inputs, enforces category-type matching and distinct transfer wallets, and writes an immutable before/after JSON snapshot to `finance_audit` inside the same transaction using the injected `AppClock`.
- **Application & Presentation (`lib/features/finance/application/finance_providers.dart`, `lib/features/finance/presentation/finance_screen.dart`)**: `financeServiceProvider` injects `databaseProvider` and `appClockProvider` into `FinanceView`, wired to the `/finance` navigation tab in `lib/app/app.dart`. `FinanceView` displays recorded balances separately from period cash flow (excluding transfers and opening balances), wallets, categories, income/expense transactions with audited edit dialogs, atomic transfers, expense-only budgets and a read-only audit trail sheet.

## Growth — Journal, Goals & Focus (Milestone 4)

Growth follows the same feature-first architecture under `lib/features/growth/`:
- **Domain (`lib/features/growth/domain/`)**:
  - `journal_models.dart`: optional `JournalMood` (neutral non-diagnostic labels), `normalizeJournalTags`, `JournalEntry` (multiple entries per date, private flag, soft-delete, requires at least one content field or mood) and descriptive `JournalSummary`.
  - `goal_models.dart`: `GoalStatus` (`planned`, `inProgress`, `completed`, `paused`, `abandoned`), `GoalProgressSource` (`manual`, `linkedHabit`, `linkedFocus`, `milestone`), `Goal`, `GoalStatusEvent`, `GoalMilestone`, `GoalProgressEntry`, `GoalProgressCalculator` (separating manual vs linked habit vs linked focus units and defensively deduplicating `(source, sourceRefId)`), and canonical reference key helpers (`buildLinkedHabitProgressRef`, `buildLinkedFocusProgressRef`).
  - `focus_models.dart`: `FocusSessionKind` (`focus`, `shortBreak`, `longBreak`), `FocusSessionState` (`running`, `paused`, `completed`, `interrupted`, `cancelled`), `FocusPreset` (25/5/15 defaults, long break after 4 completed focus sessions), `FocusSession` (deterministic `elapsedSecondsAt`, `remainingSecondsAt`, `isDeadlineReachedAt`), `FocusCyclePlanner` (interrupted/cancelled sessions never advance the 4-session cycle), `FocusHistorySummary` and `formatFocusClock`.
- **Data (`lib/features/growth/data/`)**:
  - `journal_service.dart` (`JournalService`): transactional multi-entry-per-day journal/mood CRUD, tag filtering, soft-delete and default private redaction.
  - `goal_service.dart` (`GoalService`): transactional goal creation with immutable `goal_status_history`, milestone management, habit linking, deduplicated manual progress and idempotent `syncLinkedHabitProgress` (verifying completed/recovered habit status via `UnifiedHabitHistoryReader` and rejecting duplicate source references).
  - `focus_service.dart` (`FocusService`): restart-safe Pomodoro session lifecycle (`startSession`, `pauseSession`, `resumeSession`, idempotent `completeSession`, explicit `interruptSession` with reason, `cancelSession` and `reconcileActiveSession`), persisting `deadline_utc_us` and `accumulated_elapsed_seconds` in SQLite and writing linked duration-habit (`habit_duration_events`) and linked goal (`goal_progress_entries`) progress at most once per completed focus session.
- **Application & Presentation (`lib/features/growth/application/growth_providers.dart`, `lib/features/growth/presentation/growth_screen.dart`)**: `journalServiceProvider`, `goalServiceProvider` and `focusServiceProvider` wire into `GrowthView` on tab index 3 (`/growth`) in `lib/app/app.dart`, offering Journal, Goals, Focus and Rewards sections with a default-off private visibility switch and leaving unfinished Milestone 6 features on `More` explicitly marked unavailable.

## Gamification (Milestone 5)

Gamification follows the feature-first architecture under `lib/features/gamification/`:
- **Domain (`lib/features/gamification/domain/gamification_models.dart`)**: versioned reward rules (`GamificationRules`, rule v1: `10 XP` completed, `5 XP` recovered, `0 XP` for failed/pending/partial/excused/notApplicable/unknown/conflict and `0 XP` for private, unclassified or reward-opted-out habits; never awards XP for finance spending/income or repeated edits, and never derives XP from dynamic normalized numeric scores), level boundaries (`LevelCalculator`: Level 1 starts at 0 XP; advancing from level `L` requires `100 × L` XP), deterministic achievement catalog (`AchievementCatalog`), immutable ledger/history models, and `GamificationAttributeCalculator` (reflecting recorded activity only, never competence or moral worth).
- **Data (`lib/features/gamification/data/gamification_service.dart`)**: transactional store on schema v16 tables (`gamification_xp_ledger`, `gamification_achievements`, `gamification_achievement_history`, `gamification_attributes`, `gamification_habit_attributes`). `reconcileAll` / `reconcileInCurrentTransaction` idempotently reconciles every recorded habit occurrence (at most one base `'award'` row per `(source_type, source_key, rule_version)` enforced by SQLite partial unique index; subsequent corrections append signed `'reconciliation'` rows to the immutable ledger) and evaluates deterministic achievements while preserving `unlocked_at_utc_us` and appending `'invalidated'` / `'revalidated'` history events if later invalidated. `CounterCorrectionWriter.commit` atomically calls `reconcileInCurrentTransaction` inside the same SQLite write transaction when gamification records exist. Global opt-out is persisted via `app_settings` (`gamification_enabled`).
- **Application & Presentation (`lib/features/gamification/application/gamification_providers.dart`, `lib/features/gamification/presentation/gamification_section.dart`)**: `gamificationServiceProvider` wires into `GamificationSection`, exposed as the `Rewards` section inside `GrowthView` on `/growth`.

## Privacy, Reminders & Data Management (Milestone 6)

Milestone 6 implements local privacy controls, schedule-aware reminders, encrypted backup/restore and private-by-default exports:
- **App Lock, Biometrics, Window Protection & Privacy Deletion (`lib/core/security/`)**:
  - `app_lock_service.dart` (`AppLockService`, `PinVerifier`, `SecureKeyValueStore`, `BiometricGateway`, `PrivacyWindowGateway`): uses vetted `package:cryptography` (`PBKDF2-HMAC-SHA256`, 100,000 iterations, 128-bit random salt, constant-time comparison) stored in Android Keystore via `flutter_secure_storage` (never exported in backups or logged), exponential backoff after 5 failed PIN attempts, optional `local_auth` Android BiometricPrompt (`FlutterFragmentActivity`), Android `WindowManager.LayoutParams.FLAG_SECURE` recent-app preview protection via `MainActivity.kt` `MethodChannel('com.example.hibi/privacy_window')`, and honest wipe-based forgotten-PIN recovery (`ERASE ALL LOCAL DATA`).
  - `app_lock_gate.dart` (`AppLockGate`): wraps `HibiApp`'s router in `lib/app/app.dart` to enforce launch and resume locking when a local PIN is enabled.
  - `privacy_deletion_service.dart` (`PrivacyDeletionService`): trigger-preserving atomic deletion (`permanentlyDeleteHabit`, `permanentlyDeletePrivateJournals`, `permanentlyWipeAllLocalData`) removing source, immutable audit and derived rows with zero foreign-key orphans while recreating all SQLite triggers inside the same transaction.
- **Schedule-Aware Local Reminders (`lib/features/reminders/`)**:
  - `reminder_service.dart` (`ReminderService`, `LocalNotificationGateway`, `FlutterLocalNotificationsGateway`): backed by `habit_reminders` (schema v17) and `flutter_local_notifications` (`^22.0.0`, `timezone`, Android `coreLibraryDesugaring` + boot receiver). Evaluates `HabitApplicabilityReader` so paused/archived/deleted/unscheduled habits skip or cancel alerts, uses generic text by default for private or unclassified habits unless `allow_sensitive_text` is explicitly enabled, never infers prayer times or location, and falls back automatically to `AndroidScheduleMode.inexactAllowWhileIdle` when exact alarms are unavailable.
- **Encrypted Backup/Restore & Private-by-Default Exports (`lib/features/data_management/`)**:
  - `backup_restore_service.dart` (`BackupRestoreService`): passphrase-encrypted backup envelope (`hibi_backup_enc_v1`) using vetted `PBKDF2-HMAC-SHA256` (100,000 iterations) + `AES-GCM-256` + SHA-256 payload digest, explicitly excluding PIN verifiers and biometric credentials; validates format/schema/checksum/columns/foreign-keys, creates a recoverable encrypted pre-restore snapshot, and restores atomically inside one SQLite transaction so invalid files never partially overwrite existing data.
  - `export_service.dart` (`ExportService`): generates unencrypted human-readable JSON, CSV bundle and PDF (`package:pdf`) reports with private records excluded by default (`includePrivate = false`) and explicit unencrypted-file privacy warnings. PDF export loads bundled `assets/fonts/NotoSansJP.ttf` offline and uses it for Japanese dates, habit names and goal titles; a missing or invalid asset fails the export instead of silently replacing text. The font is distributed under SIL OFL 1.1 in `assets/fonts/OFL.txt`. It is not a guarantee of glyph coverage for every language or symbol.
  - `privacy_reminders_data_screen.dart` (`PrivacyRemindersDataView`): mounted on `/more` (tab index 4) in `lib/app/app.dart`.

## Historical correction design (historical proposal; partially superseded)

The current `CounterHabitWriter` only appends future versions and rejects same-day/backdated edits. An internal counter occurrence store retrieves or creates an occurrence on demand, an internal progress writer appends same-day events with creation audit, and an internal recovery writer appends bounded current-day recovery entries for explicitly failed prior occurrences. No historical progress correction, correction preview, confirmation, audit access control or derived-data reconciliation exists. Do not expose correction or treat direct SQL and `CounterTargetStore` as an authorized correction path.

1. **Propose and preview.** A typed correction command identifies the habit, requested half-open local date range `[start, end)`, proposed fields and optional reason. Validate the dates, source versions, lifecycle/schedule boundaries and type/unit compatibility. Read a consistent snapshot and show the original and proposed values, affected dates, existing occurrence/item/event/recovery records and their counts, and any potentially affected scores, streaks, rewards and achievements. Explicitly show unknown or unavailable impact; do not present missing records as failures or invent occurrences. Show an unbounded end explicitly if applicable. A private habit's preview follows private-data access rules.
2. **Explicit confirmation.** Show an English confirmation step describing the affected range, historical records and potential statistics/reward changes; cancellation performs no writes. Bind confirmation to the exact proposed change and read-set snapshot, including versions, lifecycle/schedule and every affected source record, not just the version ID. Any source change or local-day boundary that changes the preview makes it stale: reject and require a fresh preview and confirmation.
3. **Commit atomically.** A correction service revalidates the confirmed proposal and snapshot inside one SQLite write transaction, including foreign keys, non-overlap, type/unit compatibility and all dependencies. Preserve full before/after versions and affected occurrence interpretations with stable IDs in append-oriented audit history, a UTC timestamp and optional reason. Apply the explicitly confirmed changes and all required derived-data reconciliation in that same transaction; on any conflict or failure, roll everything back. Do not reinterpret incompatible tracking types or units or silently rewrite prior results.
4. **Historical representation.** The current `habit_versions` table has non-overlap triggers; counter occurrences reference versions and preserve target/unit snapshots, but correction preimages are not yet stored. Before implementing corrections, design and migrate to a representation that keeps old configuration and occurrence preimages addressable while maintaining a non-overlapping active timeline. Keep original event/recovery data and any confirmed result history; corrections must not delete or rewrite source events silently. Resolve ID and foreign-key remapping explicitly and audit it.
5. **Recalculation boundary.** Derive affected occurrences from the confirmed range and dependency graph, including prior-date recoveries and downstream streak state. Recompute scores, coverage and reports for impacted periods; reconcile rewards by occurrence and rule version without duplicates, and preserve achievement unlock history while updating validity. These systems are not yet implemented: when they exist, corrections must either reconcile all affected persisted/derived state atomically or refuse to commit. Never claim a recalculation happened where no engine exists.

No correction schema or API is introduced by this design. Audit snapshots may contain sensitive habit data; respect private-access and privacy-deletion requirements and never write them to diagnostic logs. See TEST_PLAN.md for acceptance scenarios.
