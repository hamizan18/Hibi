# Business rules

All rules below describe planned behavior unless implemented and verified in the active milestone.

## Dates and scheduling

The day changes at 00:00 local device time. Store ISO `YYYY-MM-DD` calendar keys separately from UTC event timestamps; retain local date and time-zone context as needed so zone changes do not reinterpret historical records. Refresh the dashboard on resume or day change without requiring the app to stay open. Inject a clock; handle leap years, month/year boundaries and zone changes.

Support daily, weekdays, anchored weekly/monthly/custom intervals, fixed date ranges and one-time schedules, future start, optional end and pause periods. Monthly nonexistent dates default to skip unless the user selects last-day fallback. Effective intervals must not overlap. Occurrence generation is deterministic and idempotent, at most one primary occurrence per habit and applicable date, with multiple events; never depend on a continuous background process.

The implemented pure recurrence evaluator and `HabitScheduleStore` support daily, selected ISO weekdays (Monday 1 through Sunday 7), custom day intervals (`IntervalSchedule`, every $N \ge 1$ days from the inclusive anchor), monthly day-of-month (`MonthlyDaySchedule`, day 1..31 with default skip for nonexistent dates or optional `lastDayFallback`), and single-day (`OneTimeSchedule`) recurrences. All require an inclusive start anchor and accept an optional exclusive end. Input is an explicit Gregorian calendar date, not a timestamp; the caller is responsible for selecting the relevant local date without reinterpreting historical dates. Invalid dates, empty or out-of-range weekday sets, non-positive interval days, out-of-range monthly days and an end at or before the anchor are rejected. `HabitApplicabilityReader` combines the stored recurrence with the effective habit version and dated lifecycle state.

## Habits and history

Habits are user-defined and can be created, edited, paused, resumed, archived and deleted. Store identity separately from effective-dated versions of name/display, type, target, unit, checklist, priority, schedule, recovery, streak, scoring, rewards and attribute associations. Occurrences reference their applicable version. Future changes never rewrite prior targets; incompatible type or unit changes never reinterpret history. Backdated changes require affected records and date range preview, impact explanation, confirmation, transactional update, audit and derived-data recalculation.

Support boolean, counter (multiple entries), duration (manual and timer), independent multi-checklist items, avoidance (multiple incidents and configurable maximum), measurement with validated units, time-based and range-based tracking. Critical target configurations must be validated and typed, not opaque unvalidated strings. Each habit supports applicable description, symbol, icon, color, category, priority, target, unit, schedule, effective dates, reminders, recovery, streak, score/reward inclusion, privacy, ordering and lifecycle.

The currently implemented counter target representation stores a positive whole-number count and a nonblank unit per habit version. Counts use signed 64-bit SQLite integers; fractional values are not supported for this type. A missing target row is unconfigured, never a zero target or inferred default. Internal counter creation requires an explicit schedule and writes the identity, initial version, target, schedule, lifecycle event and creation audit in one transaction. The active lifecycle event is effective on the selected start date, including future starts; dates before the first version are not applicable. No separate scheduled lifecycle event is inferred. A strictly future version also requires an explicit schedule, which is written and audited with the version, target and optional `HabitMetadata` atomically via `CounterHabitWriter.scheduleVersion` and exposed on Today through `CounterFutureVersionControls`. For all seven non-counter tracking types (`checklist`, `avoidance`, `boolean`, `duration`, `measurement`, `timeOfDay`, `range`), `NonCounterVersionService` and `NonCounterVersionAndAuditControls` schedule strictly future versions (closing the latest open version of the same tracking type, persisting the new typed target or checklist items, schedule and optional metadata, and writing a `schedule_version` before/after snapshot in `habit_version_audit`) and expose a read-only version/lifecycle/audit inspector (`NonCounterAuditHistorySheet`). The old schedule and metadata remain attached to their version; an absent legacy schedule or metadata stays absent and is represented as null in the audit. A schedule ending on or before its version start is rejected. Historical counter target corrections are previewed and confirmed via `CounterCorrectionControls` (`CounterCorrectionPreviewer` and `CounterCorrectionWriter`).

Scheduled habits do not apply before start; paused periods do not count as expected. Resumption retains history; archives remain historically accessible. Soft-delete by default; hard deletion requires explicit confirmation, explains impact, leaves no orphans and handles sensitive audit/derived data. Pause/archive updates future reminders. Lifecycle requires dated events, not only an active flag.

The internal lifecycle store appends one effective-dated event per habit per date, with previous/new state, optional reason and UTC creation time. A first event may be `scheduled` or `active`; subsequent transitions are `scheduled` → `active`/`paused`/`archived`/`deleted`, `active` → `paused`/`archived`/`deleted`, `paused` → `active`/`archived`/`deleted`, `archived` → `active`/`deleted`, and `deleted` → `active`. Events must be appended on later dates and not backdated; inserting an event that could reinterpret an existing later occurrence is rejected. `CounterLifecycleActionService` wraps these transitions with semantic precondition checks (`pause` from `scheduled`/`active`, `resume` from `paused`, `archive` from `scheduled`/`active`/`paused`, `softDelete` from `scheduled`/`active`/`paused`/`archived`, and `restore` from `archived`/`deleted`) and returns the updated `CounterHabitConfiguration` in one transaction while preserving all historical records. These are internal services, not a completed lifecycle UI, correction flow or reminder integration.

An explicitly confirmed pause from the initial start is a narrow exception to the ordinary one-event-per-date timeline. Before or on the start date, the service may append a separate immutable pause record linked to the original initial active event, provided the initial event is still the only lifecycle event, the first version starts on that date and no occurrence exists. Effective lifecycle reads show the original active event followed by the pause on the same date; the habit remains not applicable before start and paused from start. The operation rejects stale confirmation, already-started dates and existing occurrences. Later resume still requires a distinct later date. It does not cancel or delete the habit.

The internal applicability reader returns `notApplicable` before the earliest known version and for a known non-active lifecycle state. An active state requires an applicable version and its stored schedule; missing lifecycle, version in a gap, or schedule produces `unknown`, never success or failure. A known active version and schedule returns `applicable` only when the recurrence matches. `HabitApplicabilityReader.describe` additionally reports the specific reason (`applicable`, `beforeStart`, `scheduled`, `paused`, `archived`, `deleted`, `unscheduled`, `missingVersions`, `missingLifecycle`, `missingActiveVersion`, or `missingSchedule`), and `HabitLifecycleReader` reads the effective lifecycle event on a date or the habit's full chronological lifecycle history.

The internal counter occurrence store evaluates a requested local date transactionally, returns any existing occurrence without rewriting its snapshot, and otherwise inserts one only when applicable and the counter target is known. An absent target produces `unknown`. An existing occurrence is returned even if current applicability is unknown or not applicable, alongside that applicability; consumers must not silently discard historical data. Repeated requests return the original occurrence and do not add progress or resolve logging status. This path is not exposed in the UI and does not run in the background.

The internal counter progress writer accepts positive whole quantities for an existing applicable occurrence on the current local date only. Past/future dates, unknown applicability, invalid quantities and totals exceeding signed 64-bit range are rejected. Each distinct event and its creation audit snapshot are committed together using one injected clock instant; a repeated event ID fails rather than adding progress again. Existing events from older database versions retain their original values without invented audit snapshots. Historical correction, recovery and a user-facing workflow remain unimplemented.

Optional editable starter templates: private Self Control/O avoidance, max 0, no recovery; Quran Reading/N, 5 pages daily with recovery; Daily Prayers/S, Fajr, Dhuhr, Asr, Maghrib and Isha independently configurable; Push Up/P, 10 repetitions daily. They can be skipped and never seed historical records. Do not infer sensitive meaning or make religious judgments. `StarterTemplateCatalog` exposes all four optional, editable starter templates (`AvoidanceStarterTemplate.selfControl`, `CounterStarterTemplate.quranReading`, `ChecklistStarterTemplate.dailyPrayers`, `CounterStarterTemplate.pushUp`), and their respective services (`AvoidanceHabitService`, `CounterHabitWriter`, `ChecklistHabitService`) instantiate them only when explicitly called without seeding historical occurrences. `BooleanDurationHabitService` and `MeasurementTimeRangeHabitService` support boolean, duration (manual and timer), fixed-scale integer measurement (`decimalPlaces` 0..6), time-of-day (minutes since midnight 0..1439) and range-based (`[minScaled, maxScaled]`) tracking. `CounterCorrectionPreviewer` and `CounterCorrectionWriter` implement read-set-bound counter target correction previews, stale-snapshot rejection across data or local-day changes, unit-reinterpretation rejection, and atomic preimage/postimage audit commits in `habit_counter_correction_audit`.

## Status, recovery, scoring and streaks

Stable states: `completed`, `failed`, `recovered`, `pending`, `partial`, `excused`, `not_applicable`. Missing is pending, never silently failed. Completed satisfies the configured target; partial has insufficient progress; failed is explicitly unsuccessful or confirmed by a rule; recovered fulfills an eligible prior deficit; excused is an explicit exemption; not applicable is unscheduled. Avoidance with no incident data is not automatically confirmed success: require daily confirmation or a configured completion rule. Validate input and disallow contradictory states; preserve checklist-level status.

The internal counter progress calculation uses the occurrence's historical target and its recorded positive integer events: no events means `pending`, a positive total below target means `partial`, and a total at or above target means `completed`. Actual totals above the target are retained. Invalid quantities and totals above signed 64-bit range are rejected rather than wrapped. A missing occurrence is not a pending record. The reader returns only recorded progress and does not decide scheduling applicability, explicit failure, recovery or exemptions; consumers must handle those separately. No status is persisted.

The internal read-only counter-day view returns schedule/lifecycle applicability separately from an optional occurrence ID, its recorded progress, any explicit resolution and any recovery records. If no occurrence exists, progress remains absent even on an applicable date; no pending record is fabricated. An existing occurrence and its progress remain visible when applicability is unknown or not applicable. Applicability describes schedule and lifecycle, not whether a missing counter target is configured. The reader does not create records or infer failure, recovery or excusal.

The internal counter resolution writer records an explicit `failed` or `excused` state for an existing applicable occurrence on the current local date. One immutable resolution record per occurrence stores the reason, UTC creation time and the target/progress snapshot at the decision. Completed progress cannot be resolved as failed or excused. Once resolved, the internal progress writer refuses further events and a second resolution is rejected; changing either requires a future correction workflow. Missing records never become failed automatically. The reader exposes resolution separately from applicability and recorded progress. No UI or correction workflow is implemented.

Recovery references the original occurrence, optional checklist item, target date, original target/progress, remaining deficit, time, quantity, note and result. Support partial/multiple recovery; never exceed the deficit or automatically count it toward today's independent target. Disable by default where recovery is meaningless; allow eligible counters and checklists.

The internal counter recovery calculation and store operate on an explicitly `failed` prior-date counter occurrence with incomplete progress (`initialDeficit = target - recordedTotal`). Unresolved, `excused` and `completed` occurrences cannot be recovered. `CounterRecoveryWriter` records positive whole-number recovery entries on the current local date only when the original occurrence date precedes today, was applicable, and the habit's latest lifecycle state on today is `active`. Multiple partial recovery entries are permitted until `remainingDeficit` reaches zero; any quantity exceeding the remaining deficit is rejected. Recovery records are immutable creation snapshots and never alter the original occurrence's same-day `habit_counter_events` or today's independent target/progress.

The internal counter-day effective-status evaluator (`interpretCounterDay` and `CounterDayReader.evaluate`) combines applicability, the applicable version's configured counter target, existing occurrence progress, explicit resolution and recovery records into `notApplicable`, `unknown`, `pending`, `partial`, `completed`, `failed`, `recovered`, `excused` or `conflict`. An applicable date without an occurrence evaluates to `pending` only when a counter target is configured for the applicable version, and otherwise `unknown`, without creating an occurrence row. An explicitly `failed` occurrence remains `failed` under zero or partial recovery and becomes `recovered` only when recovery entries satisfy the full deficit. Any contradictory historical state (such as records on `unknown` or `notApplicable` dates, resolution/progress snapshot mismatches, or invalid recovery records inserted via raw SQL) evaluates to `conflict` while keeping all underlying records accessible. `CounterDayRosterReader` evaluates all stored habits for a requested local date in deterministic creation/ID order within one read transaction, pairing each habit's effective version metadata (if any) with its `CounterDayEvaluation` without writing data. `CounterHistoryReader` evaluates inclusive `[startInclusive, endInclusive]` date ranges for a habit in one read transaction and lists prior-date `failed` occurrences that still have a positive `remainingDeficit` when the habit is currently `active`. `CounterRangeSummary` aggregates per-status day counts (`applicableDays`, `notApplicableDays`, `unknownDays`, `conflictDays`, `pendingDays` split into missing-occurrence vs recorded-zero, `partialDays`, `completedDays`, `failedDays`, `recoveredDays`, `excusedDays`) and keeps `recordedQuantityTotal`, `recoveredQuantityTotal` and `remainingDeficitTotal` strictly separate while excluding `conflict` rows from valid quantity totals. `CounterConfigurationReader`, `CounterAuditReader` and `CounterHabitOverviewReader` provide transactional read-only inspection of partitioned version timelines, all five persisted audit streams, and combined overview snapshots without mutating data or inventing defaults. `CounterTodayActionService` atomically coordinates current-day occurrence retrieval/creation with same-day progress or explicit resolution (rolling back any newly created occurrence on failure) and prior-deficit recovery.

Priority weights Critical 4, High 3, Normal 2, Low 1. Weighted score = 100 × sum(weight × multiplier) / sum(eligible weights): completed 1, recovered 0.75, partial normalized and clamped, failed 0; pending, excused and not applicable excluded. Allow per-habit exclusion; show recording coverage separately and item-level checklist coverage. No eligible data means No Data, not 0% or 100%; incomplete recording must not look fully successful. Scores do not measure human worth or faith.

The implemented Milestone 2 analytics domain and data services (`DailyWeightedScoreCalculator`, `AnalyticsPeriodReportCalculator`, `UnifiedHabitHistoryReader`, `AnalyticsReportReader`) enforce these rules deterministically across all eight tracking types. `UnifiedHabitDayEvaluation` normalizes counter (`recordedTotal / target`), checklist (`(completedCount + 0.75 * recoveredCount) / activeItems`), and duration (`recordedSeconds / targetSeconds`) partial progress into `[0.0, 1.0]`, excludes `pending`, `excused`, `notApplicable`, `unknown`, `conflict` and habits with `includeInScore == false` from `eligibleWeightSum`, returns `ScoreAvailability.noData` (`weightedScorePercent == null`) when `eligibleWeightSum == 0`, flags `isIncompleteRecording` whenever `pendingApplicableCount > 0`, and computes separate habit-level `recordingCoveragePercent` and item-level `checklistItemCoveragePercent`.

Streaks follow scheduled occurrences, not raw calendar days. Configurable accepted statuses include completed-only and completed-plus-recovered. Unscheduled, paused and excused dates normally neither increment nor break; past pending makes the streak unresolved, current pending does not immediately reset it, confirmed failure breaks it. Recalculate after corrections.

The implemented `HabitStreakEvaluator` and `HabitStreakReader` evaluate a habit's chronological dates from its earliest version start through `asOfDate`: `notApplicable` (unscheduled/before-start/paused/archived/deleted) and `excused` dates are skipped without incrementing or breaking; `completed` increments in both modes; `recovered` increments in `StreakCompletionMode.completedAndRecovered` and breaks in `StreakCompletionMode.completedOnly`; `pending` on `asOfDate` preserves the accumulated streak (`StreakResolutionState.activePendingToday`), whereas `pending` on a past applicable date (`date < asOfDate`) marks the streak `StreakResolutionState.unresolved` and records `unresolvedPendingDates`; confirmed `failed` (or past `partial`) resets `currentStreak` to `0` (`StreakResolutionState.broken`). Because scores, coverage, heatmaps, reports and streaks are derived on demand from the authoritative occurrence/event/resolution/recovery tables, confirmed historical counter target corrections immediately recalculate them, and `AnalyticsCorrectionImpactReader` previews the exact before/after daily weighted scores and streaks prior to confirmation.

## Finance, journal, goals, focus and rewards

Store IDR as integer rupiah. Balance = opening + income − expense + incoming transfers − outgoing transfers. Transfers are atomic, never income/expense, and cannot target the same wallet. Validate amount, date, category, wallet and type; audit historical changes. Budgets apply to explicit periods/categories and expenses only; no automatic rollover unless enabled. Distinguish cash flow from balance and incomplete records from total finances.

Journal/mood are optional, support multiple entries per date, tags, gratitude and reflections, and never penalize absence or diagnose. Goals have planned, in-progress, completed, paused or abandoned status, optional milestones and linked habits; prevent duplicate manual/linked progress and retain history. Focus/Pomodoro defaults are 25/5/15 minutes with a long break after four sessions; persist deadline/elapsed state for restart, distinguish interruption and prevent duplicate progress/rewards.

Gamification uses versioned rules and an idempotent ledger: defaults 10 XP completed, 5 recovered, zero failed/pending/excused/not-applicable; only one reward per eligible occurrence, reconciled on correction. Level 1 starts at zero; advancing from level L requires 100 × L XP. Achievements must be deterministic; preserve unlock history even if later invalidated. Custom attributes reflect activity, not competence or moral worth. No XP for spending, larger income or repeated edits; permit opt-out, especially for private/religious habits, and avoid punishment or manipulation.

## Notifications, imports and audit

Reminders are local, schedule-aware, user-configured and rescheduled on changes; handle permission, reboot and Android scheduling constraints. Use inexact fallback when exact alarms unavailable and never guarantee delivery. No automatic prayer times. Private text is generic by default.

Audit significant creation, changes, lifecycle and historical corrections with entity, operation, old/new values, timestamp and optional reason; transact with related writes, omit secrets and enforce private access. Ordinary audit is append-oriented; privacy deletion also addresses sensitive audit data.

Optional legacy import requires parsing, user mapping of symbols and start dates, preview, explicit resolution of duplicate dates/conflicts, confirmation, transactional import and recalculation with summary. Missing data stays missing/pending; never fabricate values, balances or incidents. Map “outcome” to expense only on user confirmation.
